# BioMars Protocol Studio：产品与构建方案

## 1. 用户想完成什么

核心用户是需要把实验目标变成有来源、可检查草稿的生命科学研究者。用户真正的问题是：“这份方法是否适用于我的对象？参数从哪里来？哪些地方还不确定？”

产品承诺：从实验需求出发，整理参考依据，生成结构清晰的 Protocol 草稿，并明确展示缺失资料与待核对内容。完整性检查不等于实验验证。

首版只聚焦 Protocol Generation。Drug、BO、Action 和设备执行不进入产品入口。

## 2. 用户旅程

1. 打开首页，直接看到“你想完成什么实验？”；一个自然语言输入框、可选资料附件、一个主要按钮。
2. 不确定如何开始时，选择一个示例填入需求，或直接打开一份明确标注的示例草稿。
3. 输入需求；细胞系、物种、范围等字段收在“补充背景”中，按需填写。
4. 查看真实阶段：理解需求、查找文献、解析全文、组织步骤、撰写草稿、检查完整性。无依据时不显示完成百分比或虚构用时。
5. 缺少论文时显示论文标题和需要的文件，上传后继续同一任务。
6. 在工作台阅读草稿，切换来源和待核对项；保留 Markdown 导出和浏览器打印/PDF。
7. 回到本浏览器的历史任务继续查看，不要求用户理解 session_id、模型路由或 agent 名称。

## 3. 页面结构与交互

| 页面 | 首要任务 | 必要信息 |
| --- | --- | --- |
| 首页 | 提交实验目标 | 输入、可选资料、示例、简短隐私说明 |
| 任务工作台 | 跟踪并审阅 | 阶段、草稿、来源、待核对内容、导出 |
| 历史任务 | 找回已有工作 | 标题、状态、更新时间 |
| 使用说明 | 了解能力与部署 | 示例/真实运行区别、资料处理、开源链接 |

首页导航仅保留品牌、使用说明、GitHub。登录、计费、团队管理暂不占用首屏。错误原位显示原因与恢复操作；未配置生成服务时明确说明并提供示例入口，不伪造运行结果。

## 4. 产品设计方向

2026-11-13 本地修订：用户选择 01 Soft Precision，并要求更强的生物医学特征。当前实现改为白底、深蓝文字、冷蓝细胞主视觉与无衬线字体；新增独立历史页和设置页，详见 [本地设计说明](BIOMEDICAL_LOCAL.md)。本轮暂不发布。以下保留首版设计记录供对照。

方向：安静、可信、偏编辑器的科研工作台。暖白背景，墨绿色强调，低对比细分隔线，足够留白；标题用有书卷感的衬线字体，正文和操作用清晰无衬线字体。文档是视觉主角，避免大面积装饰和卡片堆砌。

参考与取舍：

- [Elicit](https://elicit.com/)：借鉴“研究问题 → 证据 → 产物”的入口组织；不复制其宣传数字或品牌资产。
- [Linear](https://linear.app/)：借鉴克制的层级和工作台密度；针对长文阅读选择浅色界面。
- [NotebookLM](https://notebooklm.google/)：参考来源与产物并列的工作方式。此处为产品设计参考，不宣称技术一致。

桌面：主文档与右侧资料面板并排；移动端：面板切换为纵向内容。键盘可操作，所有输入有标签，错误使用 live region，支持 reduced-motion，触控目标至少 44px。

## 5. 构建方案

保留 Python 生成引擎，建立轻量 HTTP 服务与独立静态前端。生成任务以隔离子进程运行，避免模型缓存、环境变量与工作目录在任务间串扰。初版单进程队列、持久化任务状态；每个浏览器有独立访客标识，任务读写检查归属。

前端使用原生 HTML/CSS/JavaScript，保持容易部署和贡献。API 使用 FastAPI。静态演示站可以独立托管；真实生成必须接入 Python 服务和服务端模型/检索凭证，不能把 Python pipeline 直接塞进静态托管或 Cloudflare Worker。

API 面向需求、任务、资料和结果；不暴露任意服务器路径。上传文件限制格式和大小，使用服务生成的路径；模型密钥仅保留在服务端。任务返回摘要和指定产物，不公开原始日志或内部配置。

## 6. 发布分期与验收

**第一阶段（本次交付）**：独立 GitHub 仓库、生成引擎提取、最小依赖、CLI、可自行部署的 Web 服务、可交互界面、公开静态演示、构建与设计文档、自动化验证。演示数据须明确标注，真实生成是否端到端验证须如实记录。

**第二阶段（真实在线试用）**：选择 Python 托管与持久化存储，注入服务凭证，实测小规模正常/缺文献/失败任务，建立额度和任务超时；邀请少量研究者试用。多实例部署前迁移到外部队列和数据库，并完成身份与数据隔离验证。

**第三阶段（开放使用）**：账号、个人配额、删除与保留策略、成本监控、源文献授权处理和服务运维。依据真实使用反馈决定是否需要编辑版本、团队功能和分享。

验收以任务完成为中心：用户能否在不读文档的情况下提交；能否区分示例和生成结果；缺全文时能否恢复；能否核对来源并导出；刷新是否丢失任务。后续记录首次提交耗时、生成完成率、全文阻塞率、恢复成功率、每次生成成本。没有实验数据前不填写目标性能数字。
